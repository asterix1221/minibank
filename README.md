# mini-bank — Этап 1 (базовая логика)

Backend на Spring Boot 3.3 / Java 21: регистрация клиента, вход по коду из SMS, внутренние
и внешние переводы, платежи по шаблону — всё построено вокруг одной и той же трёхшаговой
машины состояний **initiate → confirm → execute**.

## Запуск через Docker Compose (основной способ)

```bash
docker compose up --build
```

Поднимает 5 сервисов в одной сети: `postgres`, `app`, `postgres-exporter`, `prometheus`,
`grafana`.

| Сервис             | Адрес                             | Комментарий                                |
|--------------------|------------------------------------|---------------------------------------------|
| Приложение          | http://localhost:8080             | API, описан ниже                           |
| Prometheus         | http://localhost:9090             | Status → Targets — проверить сбор метрик   |
| Grafana            | http://localhost:3000             | `admin` / `admin` — **это пароль по умолчанию для тестового стенда, смени его перед боевым использованием** |
| postgres-exporter  | http://localhost:9187/metrics     | сырые метрики Postgres, в основном для отладки |
| Postgres           | localhost:5432                    | `minibank` / `minibank`                    |

Проверено на голом Docker Engine (Linux/WSL2), не на Docker Desktop — так требовало ТЗ
этапа 2. **Если ты на Windows с Docker Desktop** — тоже должно работать (Desktop сам
поднимает `host.docker.internal`), но именно на голом Linux Engine это не тестировалось
мной вживую.

## Запуск без Docker (только Java, для отладки бизнес-логики)

```bash
# 1. Postgres
docker run --name minibank-pg -e POSTGRES_DB=minibank -e POSTGRES_USER=minibank \
  -e POSTGRES_PASSWORD=minibank -p 5432:5432 -d postgres:16

# 2. Сборка и запуск
mvn clean verify
mvn spring-boot:run
```

Приложение слушает `:8080`. Flyway при старте сам накатывает `V1__init_schema.sql`.

Переменные окружения (все опциональны, значения по умолчанию совпадают с командой docker
выше): `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`.

## Баги, найденные в результате реального тестирования (исправлены)

Ниже — реальные баги, найденные не мной при статическом ревью, а после того, как ты
прогнал(а) приложение вживую (docker compose + Postman + Grafana). Все уже исправлены в
этой версии кода:

1. **`/actuator/prometheus` требовал авторизацию.** В `SecurityConfig` в списке
   публичных эндпоинтов был только `/actuator/health`, а `/actuator/prometheus` и
   `/actuator/metrics` — нет. Prometheus физически не может прислать `X-Session-Token`,
   поэтому каждый его запрос получал `401`, таргет `mini-bank-app` показывал `DOWN`, а
   дашборды JVM/Spring Boot в Grafana показывали `N/A` — при том что сам datasource был
   подключён нормально. **Исправлено** — эти пути добавлены в список публичных.

2. **Некорректный path-параметр (например, буквальная строка `"null"` в URL) отдавал
   голый 500** вместо аккуратной ошибки, потому что в `GlobalExceptionHandler` не было
   обработчика для `MethodArgumentTypeMismatchException`. Добавлен.

3. **Главная причина обеих проблем выше: в спецификации нигде нет способа положить деньги
   на счёт.** Свежезарегистрированный счёт всегда стартует с балансом 0, а все остальные
   эндпоинты только двигают уже существующие деньги между счетами. Из-за этого шаг
   перевода в Postman-коллекции (и в curl-сценарии этого README, и в `smoke-test.sh`/
   `smoke-test.ps1`) отправлял перевод на 100.00 со счёта, на котором было ровно 0.00 —
   что закономерно давало `422 INSUFFICIENT_FUNDS`. Дальше id транзакции подставлялся как
   буквальная строка `"null"` (раз он не пришёл в ответе), это цепляло баг №2 выше и
   давало волну 500-х ошибок.

   **Исправлено** добавлением `POST /accounts/{accountId}/deposit` (защищённый эндпоинт,
   пополняет свой же счёт) — это тестовое удобство, а не настоящая банковская функция; ни
   у чего другого в этом домене нет понятия «внешнее пополнение». `smoke-test.sh` /
   `smoke-test.ps1` и Postman-коллекция (папка `Auth`, запрос «Fund Client A (test only)»)
   теперь вызывают его перед первым переводом.

4. **Отдельно, уже после этого:** в `docker-compose.yml` для сервиса `prometheus` была
   строка `extra_hosts: host.docker.internal:host-gateway`, добавленная для мониторинга
   Gatling на голом Linux Engine. На Docker Desktop для Windows это, судя по всему,
   конфликтовало со встроенным автоматическим `host.docker.internal` и роняло сам
   контейнер Prometheus (отсюда "Error querying page data" на `localhost:9090/targets` и
   "No data" во всех графиках Grafana — Prometheus был недоступен целиком, это не баг
   именно графика Active sessions). **Убрано** — на Docker Desktop `host.docker.internal`
   и так работает из коробки без этой строчки.

Если тянешь это обновление — нужен свежий **`docker compose up --build`** (образ
приложения пересобирается заново) и переимпорт обновлённой Postman-коллекции.

## Архитектурные решения и допущения

Списки полей и эндпоинтов в ТЗ считались минимумом, а не потолком. Каждое место, где код
выходит за рамки буквального ТЗ, отмечено комментарием прямо в коде, и продублировано
здесь:

- **`Client.registrationCode` / `registrationCodeExpiresAt`** — в ТЗ не сказано, где
  хранить код подтверждения регистрации. Добавлено прямо в `Client` (по аналогии с тем,
  как `Session` хранит свой код), так как `registrationId == Client.id` 1:1.
- **`Transaction.clientId`** — денормализованное поле владельца, не из буквального списка
  полей в ТЗ — чтобы проверки владения и поиск по idempotency-key не требовали джойна
  через `Account`.
- **`Transaction.paymentTemplateId`** — nullable, заполняется только для
  `PAYMENT_TEMPLATE`-транзакций, чтобы можно было проследить платёж до его шаблона.
- **`POST /templates`** — в ТЗ есть только `GET /templates` и `GET /templates/{id}`. Без
  эндпоинта создания «платёж по шаблону» невозможно протестировать end-to-end, поэтому
  добавлен минимальный защищённый `POST /templates`.
- **`GET /accounts/me`** — нигде в ТЗ клиент не может узнать UUID своего же счёта;
  подтверждение регистрации отдаёт только человекочитаемый `accountNumber`, а всем
  эндпоинтам переводов/платежей нужен именно UUID. Добавлено, только чтение, требует
  авторизации.
- **`POST /accounts/{accountId}/deposit`** — в ТЗ вообще нет способа завести деньги в
  систему извне; каждый счёт стартует с 0 и так и остаётся, пока на него не переведут с
  другого счёта. Без этого ни перевод, ни платёж нельзя протестировать end-to-end (нашли
  это на практике — см. раздел про баги выше). Тестовое удобство, не банковская функция.
- **Комиссия внешнего перевода** — плоский, настраиваемый процент
  (`minibank.transfer.external-commission-percent`, по умолчанию 1%), начисляется поверх
  `amount` и удерживается вместе с ним (`amount + commission`). У платежа по шаблону
  комиссии нет (в ТЗ комиссия упомянута только для внешних переводов).
- **Истечение TTL для confirm/execute проверяется лениво**, а не отдельным фоновым
  проходом: первый же вызов `confirm` или `execute` после истечения окна переводит
  транзакцию в `EXPIRED` и снимает холд, вместо отдельного scheduled-job'а, обходящего
  все строки `PENDING`/`CONFIRMED`. Единственная явно описанная в ТЗ фоновая задача — это
  симулятор внешней обработки.
- **`sessionId` в MDC** берётся буквально из значения заголовка `X-Session-Token`, как и
  написано в ТЗ («sessionId из заголовка X-Session-Token»), хотя технически в этом
  заголовке лежит bearer-токен сессии, а не `Session.id`.
- **`AccountAccessDeniedException`** (название из ТЗ, лежит в `common.security`)
  переиспользуется для любого 403 «это не твой ресурс» — не только для счетов буквально,
  но и для транзакций и шаблонов платежей — вместо отдельного исключения на каждый тип
  ресурса.
- **Простые UUID-поля вместо JPA `@ManyToOne`-связей** везде (`Account.clientId`,
  `Transaction.fromAccountId` и т.д.) — так пессимистичная блокировка остаётся явной
  (`findByIdForUpdate`) и не возникает сюрпризов с ленивой подгрузкой/N+1.
- **`@Transactional(noRollbackFor = InvalidConfirmationCodeException.class)`** на пути
  подтверждения — неверный код должен и сохранить статус `FAILED` (по машине состояний из
  ТЗ), и вернуть вызывающему HTTP 422, а для этого нужно подавить стандартный
  rollback-при-исключении именно для этого типа исключения.
- **Порядок блокировки по UUID** во внутренних переводах (`fromAccount`/`toAccount`
  блокируются в порядке `UUID.compareTo`) — предотвращает deadlock, когда два перевода
  одновременно двигают деньги между одной и той же парой счетов в разные стороны.

## Структура пакетов

`client`, `auth`, `account`, `transaction`, `transfer`, `payment` — пакеты по фиче
(entity → repository → service → controller, плюс `dto`). `common` — сквозные вещи:
`exception` (иерархия бизнес-исключений + `GlobalExceptionHandler`), `security`
(авторизация по токену сессии), `correlation` (фильтр для MDC-логирования), `metrics`
(бизнес-метрики, добавлены на этапе 2).

# Этап 2 — Docker Compose + мониторинг

## Проверка, что всё реально работает

1. `curl http://localhost:8080/actuator/prometheus | head -30` — должен сразу вернуть
   метрики в формате Prometheus, ещё до каких-либо действий в приложении (JVM/HTTP-метрики
   собираются автоматически).
2. Prometheus → `localhost:9090/targets` — и `mini-bank-app`, и `postgres` должны быть
   `UP`.
3. Прогони curl-сценарий из раздела «Этап 1» выше (регистрация, логин, перевод). После
   этого:
   ```bash
   curl -s http://localhost:8080/actuator/prometheus | grep transactions_total
   curl -s http://localhost:8080/actuator/prometheus | grep operation_duration_seconds
   curl -s http://localhost:8080/actuator/prometheus | grep auth_attempts_total
   ```
   Все три команды должны показать хотя бы одну строку с метрикой.
4. Grafana → Connections → Data sources — `Prometheus` должен уже быть в списке,
   указывать на `http://prometheus:9090`, без ручной настройки (провижининг из
   `grafana/provisioning/datasources/datasource.yml`).

## Бизнес-метрики (`common/metrics/BusinessMetrics`)

Внедрены в сервисный слой, а не в контроллеры — чтобы отражать бизнес-факт, а не сам факт
HTTP-вызова:

- `transactions_total{type, status}` — инкрементируется один раз, в момент перехода
  транзакции в терминальный статус (`COMPLETED`/`FAILED`). Вшито в
  `TransactionEventRecorder`, поскольку через него и так проходит запись каждого
  перехода (аудиторское событие `TransactionEvent`) — одно место, забыть нельзя.
- `auth_attempts_total{result}` — инкрементируется в `AuthService.confirm()`: `success`
  при верном коде, `failure` при неверном/просроченном. Идемпотентный повтор
  подтверждения уже подтверждённой сессии новой попыткой не считается.
- `operation_duration_seconds{operation, type}` — оборачивает целиком `initiate`,
  `confirm` и `execute` в `InternalTransferService`, `ExternalTransferService` и
  `PaymentService` через `BusinessMetrics.timed(...)`.

Всё остальное (`http_server_requests_seconds`, `jvm_*`, `process_cpu_usage`,
`hikaricp_connections_*`) собирается автоматически, как только `micrometer-registry-prometheus`
на classpath и открыт `/actuator/prometheus` — отдельно для этого ничего не писалось.

## Дашборды Grafana

**Три JSON-файла готовых дашбордов (id 4701, 12900, 9628) с grafana.com скачать не
удалось** — в среде, где это писалось, не было сетевого доступа к этому домену, и по
явной инструкции ТЗ на этот случай JSON не выдумывался. Поэтому:

- **Сделано**: только автоматический провижининг datasource
  (`grafana/provisioning/datasources/datasource.yml`). Grafana подключается к Prometheus
  без единого ручного действия в UI.
- **Не сделано, нужен ручной импорт**: сами три дашборда. В Grafana:
  **Dashboards → New → Import**, вставить id по одному, выбрать datasource `Prometheus`,
  когда попросит:
  - `4701` — JVM (Micrometer): память heap/non-heap, паузы GC, число потоков, загрузка
    классов.
  - `12900` — Spring Boot Statistics: throughput/latency запросов по эндпоинтам, пул
    соединений Hikari, общее состояние Spring Boot.
  - `9628` — PostgreSQL Database: соединения, транзакции/сек, cache hit ratio, размеры
    таблиц (через `postgres-exporter`).
- `grafana/provisioning/dashboards/dashboard.yml` уже включает файловый provider — если
  положишь JSON этих трёх дашбордов в `grafana/dashboards/`, они подхватятся сами при
  следующем перезапуске Grafana, без правок конфига.

Пока дашборд не импортирован, кастомные метрики (`transactions_total`,
`operation_duration_seconds`, `auth_attempts_total`) видны напрямую через Prometheus
(`localhost:9090/graph`, например запрос `transactions_total`) или через **Explore** в
Grafana по datasource Prometheus — дашборд для этого не обязателен.

## Архитектурные решения (этап 2)

- **Docker healthcheck есть только у `postgres` и `app`.** В ТЗ явно требуется healthcheck
  только для `postgres` (`pg_isready`, чтобы `app`'s `depends_on: condition:
  service_healthy` было на что опереться). Для `app` тоже добавлен (`wget --spider
  .../actuator/health`) — это низкий риск (образ свой, alpine+wget — надёжная пара) и
  прямая польза. Специально **не** добавлялись healthcheck'и для `prometheus`, `grafana`
  и `postgres-exporter` — не было возможности проверить в песочнице, есть ли в их образах
  вообще `wget`/`curl` (некоторые специально не кладут шелл/утилиты ради меньшей
  поверхности атаки), а неверно угаданная команда health check заставила бы `docker
  compose up` зависать или ложно показывать unhealthy. Их работоспособность вместо этого
  проверяется так, как и описано в DoD самого ТЗ: Prometheus — через `/targets`, Grafana —
  через факт подключения datasource.
- **`GF_SECURITY_ADMIN_PASSWORD=admin`** — оставлен как простой видимый дефолт, а не
  секрет в отдельном env-файле, именно потому что это одноразовый локальный тестовый
  стенд по ТЗ; README явно это проговаривает, а не тихо выдаёт похожий на боевой секрет.
- **`TransactionEventRecorder` теперь принимает саму сущность `Transaction`**, а не
  `(id, status)` по отдельности (сигнатура поменялась по сравнению с этапом 1) — нужен
  `getType()` для тега метрики `transactions_total`, а в момент вызова у каждого места и
  так уже есть вся сущность на руках, так что это оказалось проще, чем прокидывать тип
  вторым параметром повсюду. Это инфраструктурная правка, машину состояний и бизнес-логику
  не затрагивает.

# Этап 3 — Postman, Gatling, мониторинг нагрузки

## Часть 1: Postman

`postman/mini-bank.postman_collection.json` + `postman/mini-bank.postman_environment.json`.
Импортировать оба файла, выбрать окружение, нажать **Run** на коллекции — она выполняется
сверху вниз без единой ручной правки переменной, в таком порядке папок:

`Registration → Auth → Internal Transfer → External Transfer → Payment by Template →
Transaction Events → Negative cases`

Каждый запрос в скрипте Tests сохраняет то, что понадобится следующему шагу
(`pm.environment.set('transactionId', pm.response.json().transactionId)` и т.д.), точно
как описано в ТЗ. Папка `Auth` также логинит второго клиента (B) и получает его accountId
— чтобы у «Internal Transfer» был реальный получатель, а у «Negative cases» — реальный
«чужой счёт» для проверки.

**Найденные по ходу дела пробелы (см. «Баги, найденные...» и «Архитектурные решения»
выше):** добавлены `GET /accounts/me` и `POST /accounts/{id}/deposit` — без них
коллекцию было физически невозможно прогнать (не было UUID счёта и не на что было
переводить деньги).

Последний запрос в «External Transfer» может ещё показывать `PROCESSING`, если выполнить
его сразу после Execute — фоновый планировщик (из этапа 1) переводит такие транзакции в
финальный статус спустя несколько секунд (~5 сек по умолчанию), просто отправь запрос
ещё раз.

## Часть 2: Gatling

Java DSL (`io.gatling.javaapi`), подключён через `gatling-maven-plugin`, **намеренно не
привязан** ни к одной фазе жизненного цикла Maven — обычный `mvn clean verify` никогда не
попытается запустить нагрузочный тест. Симуляции лежат в
`src/test/java/gatling/simulations/` (проверено по актуальной документации плагина для
Java-проектов — конвенция директории менялась между версиями плагина, как и
предупреждало ТЗ, поэтому проверялось, а не бралось на веру; `simulationsFolder` также
явно прописан в `pom.xml`, чтобы не осталось сомнений). Конфиг/feeder'ы — в
`src/test/resources/` (`gatling.conf`, `data/clients.csv`).

### Подготовка тестовых данных

`load-testing/seed-test-data.sh` (Linux/macOS/Git Bash) или `load-testing/seed-test-data.ps1`
(Windows PowerShell) — сидируют N клиентов+счетов **напрямую через SQL**
(`load-testing/sql/seed_load_test_data.sql`), в обход API регистрации.

**Это значит, что засеянные строки не проходили Bean Validation из `RegisterRequest`** —
они сконструированы так, чтобы уже соответствовать её формату (телефон вида
`+7900XXXXXXX` и т.д.), но фактически приложение это никогда не проверяло. Это явно
разрешённый ТЗ более быстрый вариант, выбранный вместо прогона 200 настоящих регистраций
через API — именно чтобы нагрузочный тест измерял пропускную способность переводов, а не
что-то ещё.

Каждый засеянный счёт получает баланс 100 000 000.00 RUB (недостаток средств не должен
быть узким местом при поиске максимума) и свою заранее посчитанную цель перевода
(следующий счёт по кольцу, с переходом в начало) прямо в CSV-feeder'е —
`src/test/resources/data/clients.csv`, колонки `phone,accountId,accountNumber,toAccountNumber`.
Прогнать один раз перед любой из двух симуляций:

```bash
# Linux / macOS / Git Bash
DB_HOST=localhost DB_PORT=5432 ./load-testing/seed-test-data.sh 200
```
```powershell
# Windows PowerShell (идёт через docker compose exec, psql на компьютере не нужен)
.\load-testing\seed-test-data.ps1 -N 200
```

### Цепочка корреляции

`MiniBankChains.java` содержит одну цепочку, которую гоняют обе симуляции — логин
(initiate → confirm, сохранить токен) → перевод (initiate → confirm с кодом,
прочитанным из `debugCode` ответа initiate → execute), точно по примеру из ТЗ. Каждое
значение, нужное следующему запросу, читается через `.check(jsonPath(...).saveAs(...))`,
ничего не захардкожено. Каждый виртуальный пользователь — одна строка из feeder'а: свой
телефон, счёт и (после логина) свой токен; ни один токен не используется на нескольких
пользователях сразу.

### Запуск двух тестов

```bash
# Тест 1 - поиск потолка
mvn gatling:test -Dgatling.simulationClass=gatling.simulations.MaxSearchSimulation \
    -DbaseUrl=http://localhost:8080 \
    -DstartUsersPerSec=2 -DusersPerSecIncrement=2 -Dsteps=15 \
    -DstepDurationSeconds=30 -DrampDurationSeconds=5 \
    -DmaxFailedPercent=1.0 -Dp95ThresholdMs=1000

# Тест 2 - подтверждение стабильности на ~70-80% от найденного в тесте 1
mvn gatling:test -Dgatling.simulationClass=gatling.simulations.ConfirmationSimulation \
    -DbaseUrl=http://localhost:8080 \
    -DtargetUsersPerSec=<70-80% от результата теста 1> -DdurationMinutes=20 \
    -DmaxFailedPercent=1.0 -Dp95ThresholdMs=1000
```

Все параметры — системные свойства, не захардкожены, как и требует ТЗ (числа, подобранные
под одну машину, бессмысленны на другой).

**Найденный максимум: не заполнено.** Прогнать обе симуляции самостоятельно я не смогла —
в песочнице, где это писалось, нет ни запущенного приложения, ни доступа к Maven Central,
чтобы даже собрать зависимости Gatling (то же ограничение, что и на всех предыдущих
этапах). Прогони `MaxSearchSimulation` сам(а), запиши, на какой ступени users/sec консоль
или HTML-отчёт впервые покажет проваленный ассерт (по error rate или p95), впиши это число
сюда, и подай ~70-80% от него в `ConfirmationSimulation`. Стартовые пороги `1.0%`
error / `1000ms` p95 — это заглушки, ТЗ само оговаривает, что их нужно откалибровать по
первому реальному прогону.

Отчёты лежат в `target/gatling/<simulation>-<timestamp>/index.html`.

### Известная история проблем с памятью контейнера `app`

Коротко, в порядке появления (чтобы не наступить на те же грабли повторно):

1. **Изначально** лимита памяти не было вообще — JVM видела всю память хоста. Под нагрузкой
   `app` иногда падал и не поднимался (`restart:` не было настроено), отчёты показывали
   массовый `Connection refused` — порт физически переставал слушаться.
2. **Первая попытка фикса** (`mem_limit: 1g` + `-XX:MaxRAMPercentage=75.0`) сделала только
   хуже: 75% от 1g — это 768 МБ под heap и всего ~256 МБ на Metaspace/потоки/native-буферы,
   а этого впритык не хватает даже в покое. Под нагрузкой JVM не падала (значит,
   `Connection refused` больше не было), а уходила в непрерывный Full GC, пытаясь удержаться
   в лимите — порт слушается, TCP принимается, но обработать запрос нечем. В отчётах это
   выглядело как **100% запросов с `Request timeout` ровно на границе клиентского таймаута
   (60000 мс)**, с самой первой секунды теста и до последней — то есть приложение было живым,
   но полностью парализованным весь прогон.
3. **Текущее состояние**: `mem_limit: 2g` + `-XX:MaxRAMPercentage=50.0` (~1 ГБ heap, ~1 ГБ на
   всё остальное) и добавлено логирование GC (`-Xlog:gc:stdout:...`) прямо в stdout
   контейнера, чтобы следующую проблему такого рода было видно сразу по логам, а не
   приходилось гадать по форме отчёта Gatling.

**Это по-прежнему не измеренные, а стартовые цифры** — я не могу прогнать нагрузочный тест
в своей песочнице (нет ни поднятого приложения, ни доступа к Maven Central). Прежде чем
запускать полный `MaxSearchSimulation`/`ConfirmationSimulation` ещё раз, стоит сделать
короткую проверку на живую нитку:

```bash
docker compose up -d --build
# подожди, пока healthcheck станет healthy
docker compose ps
# в отдельном терминале - последи 30-60 секунд за памятью в покое и под лёгкой нагрузкой
docker stats mini-bank-app-1
# и параллельно устрой немного искусственной нагрузки, например
```bash
# Linux / macOS / Git Bash
for i in {1..50}; do curl -s -o /dev/null http://localhost:8080/actuator/health; done
```
```powershell
# Windows PowerShell
1..50 | ForEach-Object { Invoke-WebRequest -UseBasicParsing http://localhost:8080/actuator/health | Out-Null }
```

Если `MEM USAGE / LIMIT` в `docker stats` уже под потолком (2g) при такой лёгкой нагрузке —
подними `mem_limit` ещё (например, до `3g`/`4g`) и/или `MaxRAMPercentage` до 60-65%, и
повтори. Логи GC (`docker compose logs app | grep -i gc`) покажут, если он опять начнёт
частить с Full GC — по ним будет видно проблему заранее, ещё до полноценного нагрузочного
теста.

Как отличать симптомы по итоговому отчёту Gatling:
- **Массовый `Connection refused`** → приложение упало и не поднялось (см. `docker inspect
  mini-bank-app-1 --format='{{.State.OOMKilled}} restarts={{.RestartCount}}'` и
  `docker compose logs app --tail 200`).
- **Массовый одинаковый `Request timeout` ровно на границе таймаута, с первой же секунды
  теста** → памяти впритык, GC не успевает, приложение живое, но "подвисшее" под нагрузкой —
  see выше, поднимай `mem_limit`/heap.
- **Плавно растущий p95 + растущий % 4xx/5xx по ходу теста, без сплошной стены одинаковых
  ошибок** → это нормальная деградация под нагрузкой, именно её и должен находить
  `MaxSearchSimulation`. Ступень **перед** тем местом, где картина превращается в один из
  двух пунктов выше — и есть настоящий потолок, его и бери за основу для 70-80% в
  `ConfirmationSimulation`, а не финальную ступень из лога.

## Часть 3: мониторинг самого Gatling

Это отдельный от этапа 2 пайплайн — здесь следим за самим инструментом нагрузки, а не за
приложением.

### Что реально проверялось, по порядку

1. **graphite-writer (основной путь по ТЗ).** Проверено на практике, а не только по
   докам, как явно требовало ТЗ: **его больше нет.** Gatling убрал встроенный
   graphite data writer в версии 3.12, вместе с зависимостью от Akka — подтверждено по
   официальным release notes 3.12 и нескольким веткам обсуждений в комьюнити. Раз
   используемая здесь версия сильно новее 3.12, `data.writers = [console, file, graphite]`
   не вариант — `graphite` больше не валидное имя writer'а. В `gatling.conf` этого
   репозитория указано только `[console, file]`, с комментарием об этом.
2. **Сторонний Prometheus-плагин для Gatling (запасной путь по ТЗ).** Искала. Все
   найденные кандидаты (`gatling-prometheus-datawriter`, `com.sky:gatling-prometheus`,
   `gatling-prometheus-grafana`) заброшены примерно с 2019 года и написаны под старый
   (до-3.12) Scala `DataWriter` SPI, которого больше не существует после удаления Akka.
   Ни один не годится для актуального Gatling — это ровно та ловушка «версия 0.0.1 от
   2018 года», от которой явно предостерегало ТЗ, только от трёх разных авторов.
3. **Первая попытка (и почему её пришлось переделать):** обычный **file**-writer
   Gatling никогда не убирали, он всегда включён, и пишет `target/gatling/<run>/simulation.log`.
   Первая версия `gatling_metrics_exporter.py` тейлила этот файл как plain-text
   tab-separated лог (`USER`/`REQUEST` построчно) — так он выглядел в старых версиях
   Gatling согласно документации и форумам. На практике на этой версии Gatling (3.14.3)
   это оказалось неверно: `simulation.log` — это компактный **бинарный**, недокументированный
   формат (проверено вживую — hexdump файла начинается с нечитаемых байт, а не с
   текстовой строки `RUN ...`). Парсер тихо не находил ни одной строки и отдавал пустые
   метрики без единой ошибки в логе.
4. **Что сделано вместо этого:** реверс-инжинирить закрытый бинарный формат — плохая идея,
   он может снова измениться на следующей версии Gatling. Вместо этого экспортёр читает
   **официальные JSON-файлы отчёта**, которые Gatling сам пишет после завершения прогона —
   `target/gatling/<run>/js/global_stats.json` (чистый JSON) и `js/stats.js` (тот же JSON,
   обёрнутый в `var stats = ...;`, с разбивкой по каждому запросу). Это тот же самый
   источник данных, из которого рендерится официальный HTML-отчёт Gatling — стабильный,
   документированный, не зависящий от версии настолько, насколько сама структура отчёта.
   Экспортёр отдаёт на `:9302/metrics`: `gatling_requests_total{request,status}`,
   `gatling_error_ratio{request}`, `gatling_response_time_ms{request,stat}` (min/max/mean/
   p50/p75/p95/p99), `gatling_mean_requests_per_second{request}`, `gatling_last_run_info{run}`.

   **Честная оговорка (важно):** это значит метрики обновляются **раз за прогон** — как
   только Gatling дописал отчёт — а не непрерывно каждые несколько секунд во время самого
   теста. Живого стриминга без Enterprise-лицензии Gatling не даёт в принципе (см. пункт 1
   выше), поэтому панели вида "Active users во времени" или "RPS во времени" убраны из
   дашборда — таких данных просто нет в открытой версии. Дашборд показывает срез
   результатов последнего завершённого прогона, что для целей ТЗ (снять метрики
   инструмента нагрузки и построить по ним графики) — достаточно.

Запускать вместе с нагрузочным тестом (его нужно стартовать уже после начала
`mvn gatling:test`, чтобы папка прогона уже существовала):

```bash
python3 load-testing/gatling_metrics_exporter.py --port 9302
```
На Windows — команда `python`, не `python3` (см. `TESTING.md`).

Работает на **компьютере пользователя**, а не как сервис в `docker-compose` — он читает
файл, который создаёт Maven на твоей машине, а не что-то внутри сети контейнеров этапа 2.
В `prometheus.yml` есть третий job, `gatling`, который смотрит на
`host.docker.internal:9302` — на Docker Desktop это работает автоматически; таргет будет
показывать `DOWN`, когда нагрузочный тест сейчас не запущен — это ожидаемо, не баг.

### Дашборд Grafana

**Искала на grafana.com дашборд для Gatling, совместимый с Prometheus-датасорсом — такого
нет.** Все найденные там дашборды для Gatling (например id 9935, 21776) сделаны под
InfluxDB/InfluxQL и не заработают на Prometheus без переписывания каждого запроса. По
запасному варианту из ТЗ на этот случай собран небольшой кастомный:
`grafana/dashboards/gatling-custom.json` — активные пользователи, запросы/сек по статусу
(ok/ko), перцентили p50/p95/p99 (через `histogram_quantile` по гистограмме экспортера),
error rate во времени, и таблица итогов по имени запроса. **В отличие от трёх дашбордов
этапа 2, этот подключается автоматически** (`grafana/provisioning/dashboards/dashboard.yml`
уже активен, так как JSON этого дашборда — мой собственный, скачивать не требовалось) —
он появляется в Grafana в папке «mini-bank» без ручного импорта.

## Архитектурные решения (этап 3)

- **Обе симуляции нагрузки гоняют только внутренний перевод**, не внешний перевод и не
  платёж по шаблону. Пример корреляции в ТЗ — именно цепочка перевода, а прогон всех трёх
  типов транзакций в одном тесте (как и сидирование через API) смешал бы разные нагрузки
  и усложнил бы интерпретацию найденного потолка. Если нужен потолок конкретно для
  внешних переводов или платежей — продублируй паттерн `MiniBankChains.internalTransfer()`.
- **Кастомный Prometheus-экспортер для Gatling, а не готовый плагин** — см. «Часть 3, что
  реально проверялось». Это было самое большое неизвестное на этом этапе, и его
  проверяли больше всего (на практике, не только по докам), как и требовало ТЗ.
- **Кастомный дашборд Grafana для Gatling, а не скачанный** — см. «Часть 3, дашборд
  Grafana». Совместимого на grafana.com нет (проверено, там всё под InfluxDB), поэтому по
  ТЗ это явно помечено как кастомное — в отличие от дашбордов этапа 2, где готовый
  дашборд был обязательным условием.
- **`gatling.version` / `gatling-maven-plugin.version` закреплены на 3.14.3 / 4.21.7** в
  `pom.xml` — найдено через веб-поиск (по спискам Maven Central), не проверено реальной
  сборкой (в песочнице нет доступа к Maven Central — то же ограничение, что и на всех
  предыдущих этапах). Стоит перепроверить на Maven Central на предмет более свежего патча
  перед реальным прогоном.
